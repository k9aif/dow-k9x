Defense Acquisition System · reference deployment

Agents prepare the acquisition package.
Humans decide at every gate.

DAS takes a capability document and moves it through the defense acquisition lifecycle: JCIDS requirements, a JROC review, Acquisition milestone readiness, a Milestone review, then Systems Engineering. Agent squads do the analysis and assemble the packages; every gate is a human decision made in K9X HIL, and the program moves on only when a person approves it. Built on the open-source K9-AIF framework.

What you'll see

Seven steps, numbered the same way as the flow diagram below. A full run takes a few minutes per stage on a single local GPU.

1JCIDSDAS

Pick a demo capability document (FIREBIRD UAV, IRONCLAD ground vehicle, SENTINEL cyber defense) and click Analyze. Three squads generate the Initial Capabilities Document (ICD) and DoDAF views, then score JROC readiness.

2JROC reviewK9X HIL

The ICD goes to K9X HIL as a review task. A person opens it, reads the ICD, and approves or rejects. The decision is sent back to DAS and recorded with the job.

3Start the next stageDAS admin

In Jobs in Pipeline, every job shows its stages and decisions. After an approval the DAS admin clicks Start Acquisition; nothing moves without a recorded approval.

4AcquisitionDAS

Agents assess readiness for the Acquisition Pathway / Milestone decision against its entry criteria and build the Milestone Review Package, including gaps and a recommendation, not a decision.

5Milestone reviewK9X HIL

The second human gate: the milestone decision authority reviews the package in K9X HIL and approves or rejects.

6Start Systems EngineeringDAS admin

Again in Jobs in Pipeline, the DAS admin starts the next stage once the approval is recorded.

7Systems EngineeringDAS

SE is reached and the job completes. In this deployment SE is a demonstration endpoint: it records the next technical review (SRR); the SE review squads are not implemented yet.

Architecture

DAS is a solution built on K9-AIF: each part extends a framework building block, and the stages talk only through events.

Router → Orchestrators → Squads → Agents

The DAS Router routes each event to a stage orchestrator (JCIDS, Acquisition, SE). Orchestrators run squads; squads run agents in order, each building on the previous agent's output. No layer knows its caller.

Event backbone (Kafka)

Stages and reviews are connected by topics, e.g. workflow.hil.das.jroc for the review task and das.jroc.replies for the decision. Only the Router publishes to stage topics.

K9X HIL

A separate human-in-the-loop system. It receives review tasks, records the human decision, and publishes it back to the system that asked. hil.k9x.ai

Decisions and results kept by job

Each stage's result and each HIL decision is stored in object storage by job id, so Jobs in Pipeline survives restarts and a decision days later still resumes the right job.

Models, local

Agents run on a local model through Ollama on a single workstation GPU; Granite Guardian adds an advisory safety check on the assembled package. No cloud model is used.

Roles

demo runs jobs and watches. admin also starts the next stage after a HIL approval: the analyst who runs a job is not the person who moves the program forward.

Scope of this demonstration

  • Input documents are synthetic and fictional (no real program or DoD data); outputs have not been reviewed by acquisition experts.
  • Systems Engineering is a demonstration endpoint; its review squads are not implemented.
  • The review loop (request changes, revise the document, re-review) is designed, not built.
  • This is a public demonstration: the logins above are shared, and runs are visible to the operator.
