# DoDAF 2.0 Operational View Family — Authoring Reference

**SYNTHETIC/ORIGINAL REFERENCE MATERIAL — an original explanatory synthesis
for retrieval-corpus demonstration, not a reproduction of any official
DoDAF publication text.**

## OV-1: High-Level Operational Concept Graphic

The OV-1 is the single most-read view in a JROC review package because it
is the first thing a reviewer sees. Its job is to answer, at a glance:
who are the operational players, what capability are they trying to
achieve, and in what environment. An OV-1 that is well-formed contains, at
minimum:

- A mission statement in plain operational language (not a system
  description).
- The operational area of responsibility and environmental context
  (terrain, domain, threat posture) that shapes the requirement.
- The capability-need-to-system linkage: which named capability need each
  major system element exists to satisfy.
- Performance parameters (KPPs/KSAs) stated at both threshold and
  objective levels, since a reviewer needs both the minimum-acceptable and
  the aspirational target to judge program risk.
- Named stakeholders and the decision authority chain, since a review
  package without an identifiable decision authority cannot be routed for
  action.

A common defect in early-draft OV-1s is populating the systems and
performance sections while leaving the mission/CONOPS section thin — this
produces a document that describes *what* is being built without
establishing *why*, which is precisely the finding a JROC reviewer is
trained to flag first.

## OV-2: Operational Resource Flow Description

The OV-2 traces how information, materiel, or other resources move between
operational nodes to accomplish the mission described in the OV-1. Each
resource flow should be traceable back to a capability need — a flow with
no corresponding capability need is either an undocumented requirement or
an artifact that should not be in the view at all.

## Common Cross-View Consistency Checks

A DoDAF 2.0 package is judged not only on individual view quality but on
whether views are mutually consistent. The most common consistency defect
across programs is an entity (a system, a node, an interface) that appears
in one view family but has no corresponding entry in the view family it
should logically connect to — for example, a system referenced in an OV-1
capability-to-system mapping that never appears in the corresponding SV-1
systems structure. This class of defect is exactly what a cross-view
consistency check is designed to catch before a package reaches a
reviewer, since it is invisible from reading any single view in isolation.
