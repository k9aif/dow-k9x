# JROC / Milestone Decision Review Package Content Reference

**SYNTHETIC/ORIGINAL REFERENCE MATERIAL — an original explanatory synthesis
of publicly known acquisition review-package practice, not a reproduction
of any specific regulation's text.**

## What a Review Package Must Establish

A defense acquisition review package presented to the Joint Requirements
Oversight Council (JROC), or to a Milestone Decision Authority, exists to
let a decision authority answer five questions without needing to track
down additional material:

1. **What operational problem is this solving?** (mission statement, area
   of responsibility, threat/operational context)
2. **What capability is being requested, and what would satisfy it?**
   (capability inventory, KPPs/KSAs at threshold and objective levels)
3. **What is the plan to prove it works?** (verification and validation
   plan, test case coverage against each requirement)
4. **Who has reviewed and endorsed this, and who decides?** (service
   component endorsements, JROC member roster, program office point of
   contact)
5. **What does it cost, and is that affordable?** (unit cost, sustainment
   cost, and how those compare to any stated affordability constraint)

## Common Reasons a Package Is Returned Without Substantive Review

Reviewers screen for package completeness before they screen for technical
merit — a technically excellent capability request in an incomplete
package is returned unread on the merits, purely on packaging grounds.
The most common completeness-screening failures are:

- A capability view with no populated performance parameters (KPPs/KSAs),
  since the decision criteria cannot be established without them.
- No documented cross-view consistency check, or a consistency check that
  ran against zero views — reviewers treat an empty or skipped consistency
  analysis as evidence the package itself is incomplete, not as a neutral
  finding.
- No identifiable decision-authority chain (JROC members, service
  component endorsements, program office point of contact).
- No verification method assigned to one or more requirements, which
  leaves the decision authority unable to judge whether the program can
  actually demonstrate compliance before fielding.

## Weapons Safety Assurance (WSA) Content Expectations

Any program integrating a weapon-release or similarly safety-critical
function is expected to document its inhibit architecture (the physical
and logical mechanisms preventing inadvertent release) and its
human-in-the-loop authorization path explicitly, cross-referenced to a
verification event. A review package that defines a safety-critical
requirement without a corresponding WSA cross-reference is treated the
same as an undocumented requirement — the presence of the requirement in
a model or database is not sufficient on its own; it must appear,
attributed, in the submitted package.
